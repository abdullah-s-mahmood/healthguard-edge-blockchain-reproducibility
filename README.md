# HealthGuard: Phase 4 Deterministic Surrogate Simulation and Reproducibility Package

This repository supports computational inspection and reproduction of the selected Phase 4 systems-performance evaluation associated with *Hybrid Edge-Blockchain Framework for Secure Healthcare Big Data Processing*. It contains a deterministic Python surrogate, configuration specifications, synthetic outputs, analysis scripts, and provenance records.

**This is a selected public reproducibility package, not the full HealthGuard platform implementation. All Phase 4 numerical outcomes are `SIMULATED`.** Latency, throughput, reliability, and bandwidth values are generated by equations with seeded pseudorandom perturbations. They are not measurements from deployed healthcare edge or blockchain infrastructure. Reproducing these files establishes computational repeatability of this surrogate, not empirical validation of the proposed architecture.

## Relationship to the manuscript and public scope

The associated manuscript describes a healthcare edge/blockchain framework. This release permits examination of the implemented surrogate comparison between the labels `healthguard` and `cloud_only`, a blockchain performance surrogate, and four sensitivity grids. The manuscript itself and the complete platform are not included. No patient-level clinical records are supplied.

The public code implements CSV generation, basic raw-data checks, descriptive statistics, paired latency tests with Holm correction, sensitivity summaries, and one table and figure. It contains no runnable iFogSim2 model, Kafka deployment, IPFS deployment, Ethereum or Hyperledger Besu network, smart contracts, physical edge execution, clinical decision pipeline, or security validation. Names of those systems in YAML files or result labels do not demonstrate their execution. Dedicated break-glass authorization tests and fault-injection scenarios listed in the matrix are not executed.

## System requirements and installation on Ubuntu/Linux

Python 3.12 is recommended to align with the recorded Python 3.12.3 environment. The runner uses modern type annotations requiring Python 3.9 or later; compatibility of the complete pinned environment with other Python versions is not established. A normal Linux workstation is sufficient for these small tabular computations. Java, Node.js, Docker, GPUs, edge devices, Kafka, IPFS, and blockchain services are not required.

The dependency pins are NumPy 2.1.1, pandas 2.2.3, SciPy 1.14.1, statsmodels 0.14.4, Matplotlib 3.9.2, seaborn 0.13.2, PyYAML 6.0.2, and pytest 8.3.3. The public entry points directly import only PyYAML, SciPy, and Matplotlib beyond the standard library; the other pins are retained environment specifications. No executable test suite is included.

From the root of an obtained checkout or extracted software archive, create an isolated copy **before executing scripts**:

```bash
sudo apt-get update
sudo apt-get install python3 python3-venv python3-pip

REFERENCE_ROOT="$PWD"
WORK_ROOT="$(mktemp -d /tmp/healthguard-reproduce.XXXXXXXX)"
cp -a "$REFERENCE_ROOT/." "$WORK_ROOT/"
cd "$WORK_ROOT"
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r analysis/requirements.txt
export MPLBACKEND=Agg
```

On Ubuntu, ensure the installed Python matches the intended environment (for example, Python 3.12 on Ubuntu 24.04). Package installation requires network access unless dependencies are cached. The commands below operate only in this temporary copy. Preserve the original checkout and archived reference outputs. The original and temporary paths should remain available in the same shell for comparison.

## Run Phase 4 and validate raw data

Validate the archived inputs in the temporary copy first, then generate and validate a new run:

```bash
python analysis/validate_raw_data.py
python scripts/run_phase4_simulation.py
python analysis/validate_raw_data.py
```

The runner prints the latest-run JSON and generates `results/raw/phase4_{primary,blockchain,sensitivity}_runs_<run_id>.csv` and `results/statistics/phase4_summary_<run_id>.json`. The run ID uses local wall-clock time with one-second resolution; repeated executions within the same second can overwrite files with that ID. It replaces the latest-run pointer and appends provenance records. A newly created `run_manifest.csv` is not part of the archived tracked files; its timestamp, seed, and hash fields are left blank, and its `PASS` label is not an independent validation result.

The validator is deliberately limited: it does not check expected row counts, full schemas, pairing completeness, configuration hashes, percentile ordering, or blockchain/sensitivity numeric values. A passing validator is not equivalent to exact reproduction.

## Verify byte-for-byte raw-data reproduction

Run this from the temporary root after simulation, in the shell holding `REFERENCE_ROOT`. It compares original archived bytes with new files selected by the generated pointer, checks row counts, and reports SHA-256 digests. It does not normalize line endings or reorder records.

```bash
export REFERENCE_ROOT
python - <<'PY'
import csv
import hashlib
import json
import os
from pathlib import Path

reference = Path(os.environ["REFERENCE_ROOT"])
latest = json.loads(Path("results/statistics/latest_phase4_run.json").read_text())
for kind, expected_rows in [("primary", 100), ("blockchain", 60), ("sensitivity", 240)]:
    archived = reference / f"results/raw/phase4_{kind}_runs_20260804_025733.csv"
    generated = Path(latest[f"{kind}_csv"])
    original_bytes = archived.read_bytes()
    new_bytes = generated.read_bytes()
    if original_bytes != new_bytes:
        raise SystemExit(f"FAIL: byte mismatch for {kind}")
    with generated.open(newline="", encoding="utf-8") as stream:
        count = sum(1 for _ in csv.DictReader(stream))
    if count != expected_rows:
        raise SystemExit(f"FAIL: unexpected row count for {kind}: {count}")
    print(f"PASS {kind}: {count} rows; SHA-256 {hashlib.sha256(new_bytes).hexdigest()}")
PY
```

blockchain   fe924a00677cd550ac96677be8fc1df05ec602b8737e397a6245e9c4cfc2cd25

All three raw datasets matched exactly. Descriptive, sensitivity-summary, and table CSVs also matched exactly. ## Experimental settings and implemented assumptions

### Configuration consumption and seeds

The runner consumes `workload_levels.device_counts`, the **first** value of `workload_levels.event_rates_per_device`, `primary_experiments[0].repetitions.measured_runs`, and `primary_experiments[3].factors.offered_tx_rate_tps` from the matrix. Architectures are hardcoded. The seed file path is hardcoded; its first ten integers (1001–1010) are used with the supplied repetition count. Remaining seeds 1011–1030 are unused. Workload YAML contributes only `primary_workload.offered_rate_formula` to the summary note, not numerical settings.

Seeds pair architecture rows by population and seed ID, but the architecture-specific random streams differ. Primary random generators use `seed * 100003 + device_count + offset`, with offsets 17 (`healthguard`) and 31 (`cloud_only`). Blockchain generators use `seed * 700001 + offered_tps`. Rate/WAN sensitivity uses `seed * 9011 + int(rate * 100 + wan_delay)`; jitter/loss combinations share perturbations at the same rate and delay. These are reproducible seeded computations. Labels such as `preregistered` in configurations, comments, and notes are retained source declarations; this package alone does not verify historical preregistration or a dated protocol freeze.

### Primary surrogate

Device populations are 100, 500, 1,000, 5,000, and 10,000 with four events/device/s, giving offered rates 400, 2,000, 4,000, 20,000, and 40,000 events/s. Each architecture/population has ten seeded rows, totaling 100.

For population `N`, load `x = N/10000`, and a seeded uniform perturbation, the cloud latency expression is `18 + 95*x + 0.55*50 + U(-1.8,1.8)` ms. The HealthGuard expression multiplies its own stream's cloud expression by `1 - g`, where `g = 0.18 + 0.07*(1 - min(x,1))`. Median latency is bounded below by 1 ms. The p95 value is the median multiplied by `1.14 + U(0.01,0.09)`; p99 multiplies p95 by `1.04 + U(0.01,0.08)`. These named quantiles are synthesized values, not percentiles calculated from event traces.

Delivery success is `0.992 - 0.025*x`, plus 0.006 for HealthGuard and `U(-0.003,0.003)`, clipped to [0.90,0.9999]. Acknowledged rate is offered rate times success; accepted rate is offered rate times 0.998 or 0.995; processed rate is acknowledged rate times 0.997 or 0.994 (HealthGuard/cloud). Duplicate ratio is a perturbed load expression, scaled by 0.85 for HealthGuard; error ratio is 0.6 times the failure fraction. Consumer lag is a synthetic nonnegative function of the offered-minus-acknowledged rate and a uniform coefficient, not an observed queue.

WAN cloud bytes equal `offered_rate * 120 * 1024`. HealthGuard bytes equal cloud bytes times `(1 - 0.80 + 0.03)`, hence the archived 77% saving is imposed by the model. The 120-second interval and 1,024-byte average payload are hardcoded arithmetic factors; no timed traffic is generated. The primary 50 ms WAN constant and filtering factors are hardcoded rather than read from network/filter YAML values.

The declared five excluded warm-up runs, 30-second warm-up/cooldown, 120-second observation, escalation to 20 runs, and 30 iFogSim repetitions are not executed. Event-type mixtures, clinical thresholds, variable payload/image generation, device/LAN delay distributions, link capacities, CPU/memory profiles, and topology are not modeled by the primary equations. No separate LAN, IPFS, blockchain, or total-system byte accounting is implemented.

### Blockchain surrogate

The six offered rates are 10, 25, 50, 100, 250, and 500 transactions/s, each with ten seeds (60 rows). With `b = min(offered_tps/500,1)`, median commit latency is `0.19 + 0.70*b + U(-0.03,0.03)` seconds, bounded below by 0.01. Multipliers synthesize p95 and p99. Successful TPS is `max(1, offered_tps*(0.98 - 0.06*b + U(-0.01,0.01)))`; failed TPS, error ratio, and pool growth are derived arithmetically. Validator behavior, consensus, transaction execution, the configured transaction mix, and access-control correctness are not simulated.

### Sensitivity grids

All grids are hardcoded in Python rather than read from the matrix.

| Grid | Factors and generated behavior | Rows |

For each combination, ten seeded values use `8 + 6.2*rate + 0.45*delay + 14*jitter + 4000*loss + U(-2.2,2.2)`, bounded below by 1; a floor-index p95 across them becomes one target value. | 144 |
| `SENS-FILTER-IMAGE` | Reduction {0,0.2,0.5,0.8,0.9}; image ratio {0,0.0001,0.001,0.005}; saving is `100*reduction - 1200*image_ratio`, clipped to [-20,95]. No actual filtering or image transfer. | 20 |
| `SENS-KAFKA` | Brokers {1,3}; partitions {3,6,12,24}; acknowledgments {1,all}; compression {none,lz4}. Throughput is `9000 + 3500*brokers + 220*partitions + 500*(lz4) - 600*(all)`. ## Result schemas, labels, and statistical interpretation

`source_class=SIMULATED` identifies generated outcomes throughout the package. `healthguard` and `cloud_only` identify surrogate formula branches. Configuration evidence labels (`RECONSTRUCTION_ASSUMPTION`, `DESIGN_TARGET`, `MANUSCRIPT_REPORTED`, `MEASURED`) describe source records; a `MEASURED` host/version entry does not turn Phase 4 outcomes into infrastructure measurements. Design targets are specifications, not demonstrated results.

The primary CSV columns are:

```text
architecture, device_count, event_rate_per_device, seed_id,
offered_rate_events_per_s, accepted_rate_events_per_s,
processed_rate_events_per_s, acknowledged_rate_events_per_s,
delivery_success_ratio, duplicate_ratio, error_ratio, consumer_lag,
critical_latency_median_ms, critical_latency_p95_ms, critical_latency_p99_ms,
wan_bytes_interval, wan_rate_mb_per_s, source_class
```

Rates are modeled events/s; ratios are dimensionless. Latencies are milliseconds, interval bytes use the modeled 120 seconds, and `wan_rate_mb_per_s` divides by `1024*1024`, so its numerical unit is **MiB/s**, despite the field's `mb` spelling. `consumer_lag` has no calibrated physical queue unit. Duplicate and error fields are independently constructed model quantities, not audit counts.

The blockchain CSV contains `offered_tx_rate_tps`, `seed_id`, `median_commit_latency_s`, `p95_commit_latency_s`, `p99_commit_latency_s`, `success_tps`, `failed_tps`, `error_rate`, `tx_pool_growth`, and `source_class`. Commit latencies are seconds, rates are modeled transactions/s, error is a fraction, and pool growth is an uncalibrated surrogate quantity.

The sensitivity CSV contains `sensitivity_id`, `factor_a` through `factor_d`, `target_metric`, `target_value`, and `source_class`. Factors are `name=value` strings; unused factors are empty. Target units follow the metric: ms, seconds, events/s, transactions/s, percentage points of saving, or synthetic lag. Rows omit seed IDs because rate/WAN values already summarize seeds and other grids are algebraic.

Descriptive outputs report `n`, mean, sample SD, median, IQR, p95, p99, minimum, and maximum across seeded rows for primary median latency, delivery ratio, and WAN rate. Percentiles use sorted index `int((n-1)*p)` with no interpolation; median uses Python's conventional median. With ten observations, p95 and p99 select the same index. These are statistics across surrogate rows, not across clinical events. No bootstrap confidence intervals are computed.

Inferential analysis pairs by `(device_count, seed_id)` and calculates `cloud_only - healthguard` median latency. Positive mean differences favor the HealthGuard formula. Shapiro–Wilk p ≥ 0.05 selects a two-sided one-sample t-test on paired differences; otherwise a two-sided Wilcoxon signed-rank test is used. Holm adjustment spans the five populations. In the t-test branch, `effect_size` is mean difference divided by sample SD (paired Cohen's d; denominator falls back to 1 if SD is zero). In the Wilcoxon branch it is **the fraction of positive differences**, not rank-biserial correlation. P-values rounded to eight decimal places may print as zero; this does not mean an exact zero probability. These tests characterize seeded model outputs and do not establish deployed-system superiority.

Sensitivity summaries pool factor combinations within each metric and report count, mean, minimum, and maximum. They do not estimate causal effects, uncertainty, interactions, or robustness to real infrastructure variability. The protocol's bootstrap, robust/mixed-effects regression, segmented saturation analysis, expanded pairing keys, and rank-biserial method are not implemented.

The table preserves selected run-level fields. In the figure, each line is the **mean of ten run-level median latencies**. Shading extends from that mean to the floor-index p95 of those same medians. It is neither a confidence interval nor the raw `critical_latency_p95_ms` series, despite the plot's broad median/p95 axis wording.

The summary JSON's bandwidth saving uses paired byte ratios; its latency improvement is the floor-index median across all 50 paired percentage improvements. These aggregate different populations and remain model-derived quantities.

## Scientific limitations

The equations encode architecture gains, filtering benefits, and load responses. Agreement with an archived result cannot independently validate those assumptions. There are no packet/event traces, queueing or consensus dynamics, calibrated hardware execution, network emulation, clinical outcome validation, or measured end-to-end integration in this release. The package cannot establish deployment scalability, security guarantees, fault tolerance, interoperability, patient safety, or operational performance. It must not be cited as evidence that Kafka, IPFS, Ethereum, Besu, iFogSim2, or physical edge hardware were experimentally deployed.

The provenance record explicitly acknowledges the surrogate substitution. Its registration and approval wording is a retained record, not external verification. Recorded host specifications and version declarations do not prove all declared dependencies were used in the archived execution. Raw data repeatability and statistical-library sensitivity should be assessed separately. Reference results and provenance are preserved for inspection rather than silently corrected by this documentation.
